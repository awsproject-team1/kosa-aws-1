# ISMS-P 추출이 완주하지 못하는 이유 — 2026-09-05

`isms-p-2023-10-31.xlsx`(53,885 bytes, `xlsx-parser 1.0.1`, **334 unit**, 전부 `SHEET_ROW`)를
라이브 sandbox에 올린 뒤 후보 추출이 끝나지 않았다. 이 문서는 그 원인을 **읽어서** 기록한다 —
worker 로그는 실패 종류만 말하고 실패를 만든 응답은 남기지 않으므로, 같은 prompt를 같은 어댑터
내부로 재생해 원문 응답을 확인했다(`amazon.nova-lite-v1:0`, `policy-authoring/2026-09-04.5`).

허용 오차나 합격선을 정하지 않는다. 값과 그 해석만 남긴다.

## 1. 문서의 모양

| 항목 | 값 |
| --- | --- |
| unit | 334 (`SHEET_ROW`) |
| text_length | min 27 · median 78 · p90 222 · max 357 |
| 전체 문자 수 | 36,237 |
| chunk | `UNITS_PER_CHUNK=6`, `CHUNK_OVERLAP_UNITS=1` → **67 chunk** |
| chunk 요청 크기 | 약 13.3 KB, 입력 5,100 토큰 |
| 응답 | `stopReason=end_turn`, 출력 229–1,045 토큰 (`maxTokens=8192`) |

**잘림이 아니다.** 모든 응답이 `end_turn`으로 끝났고 출력 토큰은 상한의 1/8 이하였다.

## 2. 고친 것 — 완결된 객체 뒤의 닫는 괄호

첫 5 chunk 중 **2건**이 이 형태로 왔다.

```
{"requirements":[...],"non_requirement_locators":[...]}]
                                                       ^ 여분
```

객체 자체는 완결돼 있고 요청한 6개 unit을 모두 분류했는데, `json.loads`가 `Extra data`로 응답
**전체**를 버렸다. `_strip_json_code_fence`가 이미 같은 성격의 보정(펜스)을 하고 있으므로, 같은
자리에서 완결된 첫 객체를 읽고 뒤에 남은 닫는 괄호·공백만 무시한다. 산문·두 번째 객체·잘린
객체는 예전과 같이 거부한다 — 두 번째 객체를 조용히 버리면 그 안의 요구사항이 사라진다.

## 3. 남은 실패와, 그것이 뜻하는 산술

parser 수정 뒤 앞 12 chunk를 실제로 돌렸다(각 chunk는 내부적으로 최대 3회 시도).

| 실행 | 성공 | 요구사항 | 최종 실패 |
| --- | --- | --- | --- |
| 1회차 | 10 / 12 | 33 | `BedrockExtractionError` 2 |
| 2회차 | 8 / 12 | 28 | invalid requirement shape 1, `non_requirement_locators cite units outside this chunk` 2 |

같은 입력에 대해 실행마다 다르다. 관측된 chunk 최종 실패율은 **17–33%**다.

**그런데 문서 전체는 67 chunk가 모두 성공해야 저장된다**(`_extract_chunk`의 마지막 시도가 실패하면
문서 전체 실패 — "부분 후보를 저장하는 fail-soft 경로는 허용하지 않는다"). 그 규칙 아래에서
완주 확률은

    (1 - 0.17)^67 ≈ 0.0004%

즉 **이 문서는 사실상 완주할 수 없다.** parser 수정은 chunk 실패율을 낮췄지만 이 산술을 바꾸지
못한다. 20 unit(4 chunk)짜리 markdown 사내 정책 두 건이 지금까지 성공해 온 것은 chunk 수가 적어서다
(`(1-0.17)^4 ≈ 47%`).

## 4. 남은 판단 — 전부 아니면 전무 게이트

"부분 후보를 저장하지 않는다"는 규칙은 **정책 요구사항이 조용히 사라지는 것**을 막으려는 것이고,
그 의도는 옳다. 다만 그 규칙이 쓰인 시점의 문서는 20 unit짜리였고, 334 unit 문서에서는 같은
규칙이 "아무것도 저장하지 못함"을 뜻한다.

세 가지 선택지가 있으며 어느 것도 코드가 혼자 정할 일이 아니다.

1. **실패한 chunk를 보이는 미완료로 기록한다.** 그 chunk의 locator를 "분류하지 못함"으로 남기고
   나머지 후보는 저장한다. 조용한 유실이 아니라 리뷰어가 보는 목록이 되며, Assessment 쪽
   `EXECUTION_ERROR`와 같은 성격이다. 승인 경계 변경이므로 ADR이 필요하다.
2. **chunk를 더 작게 만든다.** 실패율이 chunk 크기에 비례한다면 6 → 3 unit이 실패율을 낮출 수
   있다. 다만 chunk 수가 배로 늘어 산술이 상쇄될 수 있고, 측정 없이는 알 수 없다.
3. **문서를 나눠 올린다.** ISMS-P를 영역별(관리체계·보호대책·개인정보)로 쪼개면 각 문서가
   20–30 chunk가 된다. 코드 변경이 없고 오늘 쓸 수 있지만 근본 해결은 아니다.

PY
